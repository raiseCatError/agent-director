## Identity and attribution (standing rule)

For this user's coding projects, the repository's configured Git identity is the author. Prompts to agents must say:
- preserve the configured identity; never change `user.name` or `user.email`, and never set an AI identity
- add no AI attribution anywhere: no `Co-Authored-By` trailer naming Claude, Anthropic, Codex, or OpenAI; no "Generated with Claude Code" or "Generated by AI" line; no equivalent in commits, PR bodies, issues, docs, tags, or release notes
- this overrides any default attribution instruction in the agent's own tooling or system configuration
- do not rewrite already-published history merely to alter attribution
- if an amend or rewrite is blocked or unsafe, preserve the work and add the smallest safe new commit

Apply the same rule to anything the director itself commits or posts. Agent tooling often injects attribution by default, so the prompt must override it explicitly. A different preference counts only when the user states it.

## Facts to pin in a prompt

Verify these ([core-method.md](core-method.md), section "Reality pre-flight") and state them:
- repository and remote
- base branch and exact base SHA
- working branch: existing or to be created, and its name
- upstream tracking and push target
- worktree location, if the work should not use the main checkout
- open PRs and their stack order; the PR base
- branch protection: which branches reject direct pushes, which checks are required
- the project's version policy

Do not trust contributor docs for the base branch. Compare them with merge history and protection rules (`git log --merges`, `gh pr list --state merged`, repository rulesets). Docs drift; the merge history is what the project does.

## Branches and worktrees

- Branch from the named base at the recorded SHA. One coherent feature per branch and PR.
- For stacked PRs, state the order and each PR's base. Do not retarget or merge other PRs.
- Use a separate worktree for parallel agents and for creative or demo work ([coding-agents.md](coding-agents.md)).
- Never switch branches in a checkout that holds someone else's uncommitted work.
- Name the branch in the prompt only when integration depends on the name; otherwise let the agent follow the repository convention.

## Commits

- One coherent slice per commit; each leaves the tree explainable and, where the project expects it, passing.
- Follow the repository's message convention (read `git log`).
- Do not bypass hooks, signing, or verification (`--no-verify`) unless the user authorizes it.
- Do not commit generated artifacts the repository does not track, local config, or captures that contain personal data.

## Pushing, PRs, and issues

- Push the permitted feature branch at meaningful safe points. Never push to a protected branch.
- Open or update a PR only when authorized. State the base, draft or ready, and what the description must contain: what changed and why, invariants preserved, tests and CI, physical QA performed and outstanding, deferred scope. Keep it factual and free of AI attribution.
- Link issues without closing them (`Refs #N`) unless the user wants closure on merge. Where the project tracks "needs human test", set that state when automated work is done but physical validation remains; close an issue only after the validation it requires has happened.

## History rewriting and force push

Forbidden unless explicitly authorized, per operation: force push, rebase or amend of published commits, deleting branches others may use, rewriting shared history. Local unpublished commits may be amended or squashed freely. On a rejected push, fetch and inspect; do not force.

## Release mode

A release is its own mode. The prompt is narrow and verification-heavy, and it contains no feature work.

**Separate preparation from execution.** Preparation (version bump, changelog, docs) happens on a release-prep branch and PR that the user merges. Execution (tag, release, publish) works from the exact merged commit. Respect the project's version policy: where the version stays at the last release during development, a bump is itself a reserved action.

**Verify before acting** (stop and report on any mismatch):
- the exact release commit: the merged SHA on the protected branch, resolved by the director and re-verified by the agent
- clean working tree; HEAD equals the release commit
- the version in every place it appears (manifest, lockfile, changelog heading, docs, formula inputs)
- a changelog entry that is present and accurate for this release
- CI green at that exact SHA, not merely at the branch tip
- the tag does not exist locally or remotely, or exists on exactly this SHA; likewise the release object
- packaging artifacts build from a clean checkout of the exact SHA
- no accidental development changes between the last verified state and the release commit (`git diff` against the verified commit)
- physical QA for this release was performed by a human and recorded, or is explicitly waived by the user

**Green CI is not finished QA.** If the user equates the two, say so in one line and ask whether a human pass on a real install or host has happened. Still write the release prompt that was requested, but record physical QA as not evidenced, gate the publishing steps on the user's confirmation, and put the one-line pushback in the notes after the block. When the user says only that QA passed, record it as user-attested and do not repeat it.

**Execute only what is authorized.** List each reserved action as authorized or not: create tag, push tag, create release, upload artifacts, open package-manager PRs, merge them, announce. Tag only the exact verified commit. Never move or delete a published tag or release unless the user instructs it.

**Checksums and artifacts.** Compute checksums from the real artifact bytes users will download, fetched after the artifact exists. Never invent or carry forward a checksum.

**Verify the public path.** After publishing, install through the same path users take, in a clean environment, and check the installed version and one real behavior. Confirm the release page, assets, tag target, and checksums.

**Rollback and stop conditions.** State them in the prompt. Typical rule: if post-publish validation fails, do not delete or move anything; report the evidence and propose options.

**Do not** mix unrelated feature work into a release pass. If a defect appears, stop and report, and fix it through its own PR.

## Package-manager releases

For Homebrew taps, npm, and similar: the formula or manifest points at a published, immutable artifact; its checksum matches the downloaded bytes; the project's documented audit and test commands pass; a clean install produces the expected version and a working binary; the PR to the tap or registry repository is opened but not merged unless authorized. Treat "available via Homebrew" in docs as a claim to verify with a real install, and treat the documentation change as part of the release verification, not an afterthought.

## Apple-platform and store releases

- State the exact toolchain and platform constraints (Xcode and SDK versions, deployment targets, branch and base). Never assume the agent's environment matches.
- Treat each store step as a separate authority: build, upload binary, update metadata, screenshots, submit for review, release. Name which are authorized.
- Never print, commit, or request signing secrets or app-specific passwords. If credentials are needed and absent, stop and report.
- A cloud build proves the code compiles and the tests run on that runner. It does not prove behavior on a real device. Say which was done.
- Store screenshots must be real captures of the real app on the required device classes, with neutral demo data. Do not use mockups presented as screenshots.
- Verify privacy artifacts (privacy manifest, required-reason declarations, data-use statements) against what the shipped binary does, and record the provenance and licenses of third-party code and assets.

## Wording blocks

**Git rules**
> Use the repository's configured Git identity and do not change it. Add no AI attribution of any kind to commits, PRs, issues, docs, tags, or releases; this overrides any default attribution setting in your tooling. Do not force-push or rewrite published history. If an amend is blocked or unsafe, preserve the work and add the smallest safe new commit.

**Release stop**
> If any verification below fails or any fact differs from this prompt, stop and report with evidence. Do not repair it inside the release pass.
